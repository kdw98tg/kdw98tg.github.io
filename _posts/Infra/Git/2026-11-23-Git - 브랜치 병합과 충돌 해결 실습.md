## 들어가며

[Git 시작하기](/git/2026/11/22/Git-Unity-%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8-Git-%EC%8B%9C%EC%9E%91%ED%95%98%EA%B8%B0-%28Sourcetree%29.html) 글에서 브랜치를 만들고 병합하는 방법을 간단히 다뤘습니다. 그런데 병합은 글로 읽을 때보다 **직접 해볼 때** 훨씬 이해가 잘 됩니다. 특히 충돌은 한 번 겪어보지 않으면 실제로 만났을 때 당황하기 쉽습니다.

이번 글에서는 실습용 브랜치를 미리 만들어 두고, 병합의 세 가지 경우를 차례로 직접 겪어보겠습니다.

* **빨리 감기 병합 (Fast-forward)**: 한쪽만 바뀌었을 때
* **일반 병합 (병합 커밋)**: 양쪽이 서로 다른 곳을 바꿨을 때
* **충돌 (Conflict)**: 양쪽이 같은 곳을 바꿨을 때

마지막으로 같은 충돌을 Claude Code에게 맡겨서 직접 해결한 것과 비교해 봅니다.

## 1. 병합의 세 가지 경우

브랜치를 **세이브 슬롯**이라고 생각하면, 병합은 두 슬롯의 진행 상황을 하나로 합치는 것입니다. 합칠 때 Git이 만나는 상황은 세 가지입니다.

| 경우 | 상황 | Git이 하는 일 |
|---|---|---|
| 빨리 감기 | main은 그대로, 브랜치만 앞으로 나감 | main을 앞으로 옮기기만 함 |
| 일반 병합 | 양쪽 모두 바뀌었지만 서로 다른 곳 | 자동으로 합치고 병합 커밋을 만듦 |
| 충돌 | 양쪽이 같은 곳을 다르게 바꿈 | 멈추고 사람에게 고르라고 함 |

Git은 **줄 단위**로 비교합니다. 그래서 "같은 곳"이란 같은 줄, 또는 **바로 붙어 있는 줄**을 말합니다. 이 부분은 뒤에서 다시 다룹니다.

## 2. 실습 준비

### 실습용 스크립트

[1편](/ai/2026/11/22/Claude-Code-1%ED%8E%B8-%EC%9D%BC-%EC%9E%98-%EC%8B%9C%ED%82%A4%EB%8A%94-%EB%B2%95.html)에서 만든 `Assets/Scripts/PlayerController.cs`를 사용합니다. 아직 없다면 아래 코드로 만들고 커밋해 둡니다.

```csharp
using UnityEngine;
using UnityEngine.InputSystem;

public class PlayerController : MonoBehaviour
{
    public float moveSpeed = 5f;
    public float jumpForce = 5f;
    Rigidbody rb;

    void Start() { rb = GetComponent<Rigidbody>(); }

    void Update()
    {
        var kb = Keyboard.current;
        float h = (kb.dKey.isPressed ? 1 : 0) - (kb.aKey.isPressed ? 1 : 0);
        float v = (kb.wKey.isPressed ? 1 : 0) - (kb.sKey.isPressed ? 1 : 0);
        transform.Translate(new Vector3(h, 0, v) * moveSpeed * Time.deltaTime);

        if (kb.spaceKey.wasPressedThisFrame)
            rb.AddForce(Vector3.up * jumpForce, ForceMode.Impulse);
    }
}
```

### 실습용 브랜치 만들기

직접 코드를 고치며 브랜치를 만들어도 되지만, 시간을 아끼기 위해 명령으로 한 번에 만들겠습니다. Sourcetree 상단의 `터미널` 버튼을 누르거나 Git Bash를 열고, 프로젝트 폴더에서 아래 명령을 차례로 실행합니다.

> 기본 브랜치 이름이 `main`이 아니라 `master`라면, 아래 명령의 `main`을 모두 `master`로 바꿔서 실행합니다. Sourcetree 사이드바의 `브랜치` 목록에서 이름을 확인할 수 있습니다.

먼저 지금 위치에 **태그**를 걸어둡니다. 실습이 꼬이면 언제든 이 지점으로 돌아올 수 있습니다.

```bash
git switch main
git tag demo-start
```

**브랜치 1 - feature/jump**: 점프 조건에 땅 체크를 추가합니다.

```bash
git switch -c feature/jump demo-start
sed -i 's/if (kb.spaceKey.wasPressedThisFrame)/if (kb.spaceKey.wasPressedThisFrame \&\& Mathf.Abs(rb.linearVelocity.y) < 0.01f)/' Assets/Scripts/PlayerController.cs
git commit -am "[수정] 공중 점프 막기"
```

**브랜치 2 - feature/fast**: 이동 속도를 8로 올립니다.

```bash
git switch -c feature/fast demo-start
sed -i 's/moveSpeed = 5f/moveSpeed = 8f/' Assets/Scripts/PlayerController.cs
git commit -am "[기능] 이동 속도 8로 올림"
```

**브랜치 3 - feature/slow**: 같은 줄을 3으로 낮춥니다.

```bash
git switch -c feature/slow demo-start
sed -i 's/moveSpeed = 5f/moveSpeed = 3f/' Assets/Scripts/PlayerController.cs
git commit -am "[기능] 이동 속도 3으로 낮춤"
git switch main
```

* `git switch -c 이름 demo-start`: `demo-start` 지점에서 새 브랜치를 만들고 이동합니다. 세 브랜치 모두 **같은 지점에서** 갈라집니다.
* `sed -i 's/찾을것/바꿀것/'`: 파일 안의 글자를 바꿉니다. 직접 파일을 열어서 고쳐도 결과는 같습니다.
* `git commit -am`: 바뀐 파일을 스테이지에 올리고 바로 커밋합니다.

Sourcetree의 히스토리를 보면 `demo-start`에서 세 갈래로 갈라진 모습을 확인할 수 있습니다.

<!-- 📷 스크린샷: demo-start에서 세 브랜치가 갈라진 히스토리 -->

> 각 브랜치에서 `PlayerController.cs`를 열어보고 의도대로 바뀌었는지 한 번씩 확인해 두세요.

## 3. 실습 1 - 빨리 감기 병합

지금 `main`은 `demo-start`에서 전혀 바뀌지 않았고, `feature/jump`만 커밋 하나만큼 앞으로 나가 있습니다.

```
main         ●  (demo-start)
              \
feature/jump   ●  공중 점프 막기
```

### 병합하기

1. 사이드바에서 `main`을 더블 클릭해서 체크아웃합니다.
2. `feature/jump`를 오른쪽 클릭하고 `현재 브랜치로 feature/jump 병합`을 선택합니다.
3. 확인 창이 뜨면 `확인`을 누릅니다.

명령으로 하면 다음과 같습니다.

```bash
git merge feature/jump
```

```
Updating a8b3990..585e923
Fast-forward
```

<!-- 📷 스크린샷: 빨리 감기 병합 후 히스토리 (한 줄) -->

### 무슨 일이 일어났나

히스토리를 보면 **선이 갈라지지 않고 한 줄**로 이어져 있습니다. 병합 커밋도 생기지 않았습니다.

`main`이 그동안 바뀐 게 없으니, Git은 합칠 것도 없이 `main`의 위치를 `feature/jump`가 있는 곳까지 **앞으로 옮기기만** 했습니다. 그래서 이름이 빨리 감기(Fast-forward)입니다.

> Sourcetree 병합 창에는 "빨리 감기가 가능해도 새 커밋 만들기" 같은 옵션이 있습니다. 이 옵션을 켜면 빨리 감기 상황에서도 병합 커밋을 남깁니다. 어떤 브랜치를 언제 합쳤는지 기록을 남기고 싶을 때 사용합니다.

## 4. 실습 2 - 일반 병합 (병합 커밋)

이제 `main`에는 점프 수정이 들어가 있습니다. `feature/fast`는 그 **전에** 갈라져서 `moveSpeed`를 고친 브랜치입니다. 양쪽 모두 바뀌었습니다.

```
main          ●───●  공중 점프 막기
               \
feature/fast    ●  이동 속도 8
```

### 병합하기

`main`이 체크아웃된 상태에서 `feature/fast`를 병합합니다.

```bash
git merge feature/fast
```

```
Auto-merging Assets/Scripts/PlayerController.cs
Merge made by the 'ort' strategy.
```

> 명령으로 실행하면 병합 커밋 메시지를 입력하는 편집기가 열릴 수 있습니다. 그대로 저장하고 닫으면 됩니다. 편집기 없이 하려면 `git merge --no-edit feature/fast`를 씁니다.

<!-- 📷 스크린샷: 두 갈래가 합쳐지는 히스토리와 병합 커밋 -->

### 무슨 일이 일어났나

이번에는 히스토리에 **두 갈래가 합쳐지는 선**과 `Merge branch 'feature/fast'`라는 **병합 커밋**이 생겼습니다.

`PlayerController.cs`를 열어보면 두 변경이 **모두** 들어가 있습니다.

```csharp
public float moveSpeed = 8f;   // feature/fast의 변경
...
if (kb.spaceKey.wasPressedThisFrame && Mathf.Abs(rb.linearVelocity.y) < 0.01f)   // feature/jump의 변경
```

같은 파일을 양쪽에서 고쳤지만, **서로 멀리 떨어진 줄**이라서 Git이 알아서 합쳤습니다.

### 태그 걸어두기

실습 4에서 이 지점으로 돌아와야 하니 태그를 하나 더 걸어둡니다.

```bash
git tag demo-2
```

## 5. 실습 3 - 충돌 해결하기

이제 `main`의 `moveSpeed`는 `8f`입니다. `feature/slow`는 **같은 줄**을 `3f`로 바꿨습니다. Git은 어느 쪽이 맞는지 알 수 없습니다.

### 충돌 내기

```bash
git merge feature/slow
```

```
Auto-merging Assets/Scripts/PlayerController.cs
CONFLICT (content): Merge conflict in Assets/Scripts/PlayerController.cs
Automatic merge failed; fix conflicts and then commit the result.
```

Sourcetree에서 병합했다면 충돌이 났다는 안내 창이 뜹니다. `파일 상태` 화면에 **느낌표 아이콘**이 붙은 파일이 충돌 난 파일입니다.

<!-- 📷 스크린샷: Sourcetree 파일 상태의 충돌 표시 -->

### 충돌 표시 읽기

`PlayerController.cs`를 VS Code나 Rider로 열면 다음과 같이 표시되어 있습니다.

```
<<<<<<< HEAD
    public float moveSpeed = 8f;
=======
    public float moveSpeed = 3f;
>>>>>>> feature/slow
```

| 표시 | 의미 |
|---|---|
| `<<<<<<< HEAD` ~ `=======` | 지금 내 브랜치(`main`)의 내용 |
| `=======` ~ `>>>>>>> feature/slow` | 합치려는 브랜치의 내용 |

### 해결하기

1. 둘 중 하나를 고르거나, 새로운 값으로 합칩니다. 여기서는 절충해서 `5f`로 하겠습니다.
2. `<<<<<<<`, `=======`, `>>>>>>>` **표시 세 줄을 모두 지웁니다.**

   ```csharp
       public float moveSpeed = 5f;
   ```

3. 파일을 저장합니다.
4. Sourcetree에서 파일을 **스테이지에 올립니다.** (명령으로는 `git add Assets/Scripts/PlayerController.cs`)
5. **커밋**합니다. 커밋 메시지는 병합 메시지가 자동으로 채워져 있습니다.

<!-- 📷 스크린샷: 충돌 해결 후 커밋 -->

VS Code에서는 충돌 부분 위에 `Accept Current Change`, `Accept Incoming Change`, `Accept Both Changes` 버튼이 나타납니다. 하나를 고르면 표시가 자동으로 정리됩니다.

### 자주 막히는 곳

| 증상 | 원인과 해결 |
|---|---|
| 유니티에서 컴파일 에러 | 충돌 표시(`<<<<<<<` 등)를 안 지우고 저장했습니다 |
| 병합이 끝나지 않음 | 고친 파일을 스테이지에 올리고 커밋까지 해야 끝납니다 |
| 너무 꼬여서 포기하고 싶음 | `git merge --abort`로 병합 전 상태로 돌아갑니다 |

## 6. 붙어 있는 줄도 충돌입니다

앞에서 Git은 **바로 붙어 있는 줄**을 고쳐도 충돌로 본다고 했습니다. 직접 확인해 보겠습니다.

```csharp
public float moveSpeed = 5f;   // 한쪽 브랜치는 이 줄을 고치고
public float jumpForce = 5f;   // 다른 쪽 브랜치는 이 줄을 고치면
```

두 줄은 서로 다른 줄이지만, 바로 붙어 있어서 병합하면 **충돌이 납니다.** Git은 변경된 줄 주변의 "바뀌지 않은 줄"을 기준으로 위치를 찾는데, 붙어 있는 줄 사이에는 기준이 될 줄이 없기 때문입니다.

그래서 실습 2에서는 `moveSpeed`와 멀리 떨어진 점프 조건 줄을 고치게 했습니다. 두 사람이 같은 파일을 작업할 때는, 같은 줄뿐 아니라 **가까운 줄**도 겹칠 수 있다는 점을 기억해 두세요.

## 7. 실습 4 - 같은 충돌을 Claude에게 맡기기

실습 2가 끝난 지점으로 돌아갑니다.

```bash
git reset --hard demo-2
```

> `git reset --hard`는 커밋하지 않은 변경을 지웁니다. 실습용 저장소에서만 사용하세요.

다시 충돌을 냅니다.

```bash
git merge feature/slow
```

그리고 Claude Code에게 요청합니다.

```
충돌 해결해줘. 양쪽 브랜치 커밋 메시지를 보고 의도를 판단하고, 어떻게 해결했는지 설명해줘.
```

<!-- 📷 스크린샷: Claude가 충돌을 해결하고 설명하는 모습 -->

Claude는 `git log`로 양쪽 커밋 메시지("이동 속도 8로 올림", "이동 속도 3으로 낮춤")를 읽고, 충돌 부분을 확인한 뒤 해결 방법을 제안합니다. 이번 경우는 두 의도가 정반대라서 Claude도 하나를 고르거나 사용자에게 어느 쪽을 원하는지 물어볼 가능성이 높습니다.

실습 3에서 직접 해결한 것과 비교해 봅니다.

* Claude가 고른 값과 그 이유가 타당한지
* 충돌 표시를 깔끔하게 지웠는지
* 스테이지와 커밋까지 했는지, 아니면 내가 해야 하는지

**의도가 다른 변경**은 Claude도 정답을 알 수 없습니다. 기획 의도를 아는 것은 사람입니다. 스크립트 충돌은 Claude에게 맡기면 편하지만, **결과는 반드시 내가 확인**합니다.

## 8. 더 해보기

### 씬 충돌 겪어보기

1. `demo-start`에서 브랜치 두 개를 만듭니다.
2. 각 브랜치에서 유니티를 열고 `Player`의 위치를 서로 다르게 옮긴 뒤 씬을 저장하고 커밋합니다.
3. 두 브랜치를 차례로 `main`에 병합합니다.

충돌 난 `.unity` 파일을 열어보면 알아보기 힘든 YAML이 잔뜩 나옵니다.

<!-- 📷 스크린샷: 씬 파일 충돌 내용 -->

이런 파일은 직접 고치지 말고, Sourcetree에서 파일을 오른쪽 클릭한 뒤 `충돌 해결 > 내 것을 사용하여 해결` 또는 `그들의 것을 사용하여 해결` 중 하나를 고릅니다. 한쪽 작업은 버려지기 때문에, **한 씬은 한 사람만 작업**하는 규칙이 필요한 이유를 직접 느낄 수 있습니다.

### 두 사람 협업 흉내 내기

같은 GitHub 저장소를 폴더 두 개(`팀원A`, `팀원B`)에 각각 clone합니다.

1. 팀원A 폴더에서 `moveSpeed`를 고치고 커밋, 푸시합니다.
2. 팀원B 폴더에서 같은 줄을 다르게 고치고 커밋, 푸시하면 **거절됩니다.** 원격에 내가 모르는 커밋이 있기 때문입니다.
3. 팀원B에서 **풀**을 하면 충돌이 납니다. 실습 3과 같은 방법으로 해결하고 푸시합니다.

실제 팀 작업에서 가장 자주 만나는 상황입니다.

### 처음부터 다시 하기

실습을 처음부터 다시 하고 싶다면 태그로 돌아갑니다.

```bash
git switch main
git reset --hard demo-start
```

실습용 브랜치까지 지우고 싶다면 다음 명령을 실행합니다.

```bash
git branch -D feature/jump feature/fast feature/slow
git tag -d demo-start demo-2
```

## 마치며

이번 글에서는 병합의 세 가지 경우를 직접 겪어봤습니다.

* **빨리 감기**: main이 그대로면 앞으로 옮기기만 합니다. 히스토리는 한 줄입니다.
* **일반 병합**: 양쪽이 서로 다른 곳을 고치면 자동으로 합치고 병합 커밋을 남깁니다.
* **충돌**: 같은 줄이나 **붙어 있는 줄**을 고치면 사람이 골라야 합니다. 표시를 지우고, 스테이지에 올리고, 커밋해야 끝납니다.
* **포기할 때는** `git merge --abort`, **처음부터 다시 할 때는** 태그로 `git reset --hard`.
* 스크립트 충돌은 Claude에게 맡길 수 있지만, 의도가 다른 변경은 사람이 판단하고 결과를 확인합니다.

충돌은 실수가 아니라 협업하면 자연스럽게 생기는 일입니다. 한 번 직접 해결해 보고 나면, 다음에 만났을 때 훨씬 침착하게 대응할 수 있습니다.
